## 1. 唯一面向家长的理想流程（目标交互）

**用户在任何与ChatGPT的对话中发：**
- 作业错题照片：例如“这题Kevin做错了，做成数学小侦探，顺便再出几道类似找错训练”；
- 截图；
- 纯文字：原题、错误答案或完整解题步骤；
- 多张错题：要求一次打包；亦可只说“把上一张错题加入数学小侦探”。

**ChatGPT应完成：**
1. 读出原题、单位、提问方式、已知条件与实际错误结果／步骤；没有的事实绝不编造；
2. 分清**真实原题证据**、**推测的错误机制**、**虚构的侦探示范步骤**；对关键题干看不清、条件不足或多解存在时，在聊天中只询问必要澄清；
3. 重新算正确结果，尽量**独立反算/图解/单位换算**；精确数值题应有机器可复验的参数化数学依据；
4. 形成一个迷你训练包，默认：
   - A：以该错题关系改编的**错误案**（找首错→修复→反向验证）；
   - B：同数学关系、**换数字或换情境**的另一错误案（检验是否真的学会）；
   - C：同类型的**正确案**（防止每题都盲目找错）。
   如某题不适合自动构造三案，不得硬凑；至少生成可审定的一案，并用已审定的其他案补足每日2错1对。
5. 将**脱敏后的结构化案件包**写入GitHub指定的“侦探收件箱”（使用已连接GitHub工具；不可假装直接写进仅本机开放的服务）；
6. 把结果真实反馈给家长：“已投递3宗训练/已待校验”“网站待同步/已确认导入”等。**GitHub提交成功不等于网站已同步成功；没有读取网站同步回执前不得声称已在网站上线。**

**网站应完成（Codex实现一次，未来无需每次介入）：**
1. 本机服务启动时，以及运行中定期检查 GitHub 侦探收件箱；
2. 严格审查JSON契约、来源、去重、数学规则与版本，再导入本机案卷；
3. 数学确定、可独立校验的案件**自动发布/加入“新收到的训练”**，家长不必逐项再填表、点三勾；不确定的题自动放入待核对队列，并把原因显示给家长，不发布给Kevin；
4. 已有今日3宗计划保持稳定；新增可用题通过儿童首页“刚收到的新案件/现在就练”立即进入，也参与以后每日计划；
5. 成功同步、重复、待审核、失败要有明白的状态；离线时沿用本地案卷，不丢数据。

### 体验对照

| | 旧方式（已经实现） | **新目标（需要Codex实现）** |
|---|---|---|
| 用户输入 | 网站后台填很多字段 | **直接在聊天中发照片或一句话** |
| 题目数学审核 | 家长在网站填答案、勾3项 | **ChatGPT检查+本机确定性校验；歧义只在聊天里确认** |
| 内容传送 | 家长手动在浏览器新增 | **ChatGPT→GitHub收件箱→网站自动拉取** |
| 网站新内容 | 家长发布才出现 | **可校验案自动上线；疑难案标待核对** |
| 实际训练 | 四步侦探、每天3案 | 保持四步，新增“立即练新收到的题” |
| Codex | 初次实现 | **只需实现一次；以后新错题不需要每次找Codex部署代码** |

**注意**：保留现有家长“手工录入”代码作为应急/离线后备，但从导航、家长说明及新手引导中降级到折叠的“高级/备用方式”，不再要求家长实际使用；也不因新功能删除其存档。

## 2. 技术路线：GitHub作为单向“内容信箱”，本机仍是数据主库

\`\`\`text
家长 → ChatGPT（发文字、截图、作业照片）
          │ 分析原题、独立复算、审定错因
          │ 转为匿名原题/虚构学生做法/提示/正确验证
          ▼
连接的 GitHub：独立数据分支 detective-inbox
   content/detective/inbox/*.json
          │（由ChatGPT写入单一文件，不需改应用源码）
          │（GitHub API 只读获取该分支的数据）
          ▼
Kevin Math Lab 本机服务（127.0.0.1:4177）
   导入器定时拉取 → JSON白名单验证 → 数学oracle → 去重/版本化
          ├─ 验证通过：自动发布，进入“刚收到的案件”
          └─ 不确定：私有待核对，不进入儿童题库
          ▼
SQLite本地存储 + 原备份/导入导出 → Kevin电脑端探案
\`\`\`

**选择这条路线的原因：**
- ChatGPT已经连接 GitHub，可在有写入权限的情况下直接提交文件；但**无法直接访问使用\`127.0.0.1\`的本机网站/NAS**；
- 对每道新错题只生成**数据文件**，不要求改TypeScript组件、重新跑全套CI、让Codex发布新版本；
- 网站出网是单向拉取，不开放公网端口、不新增家庭网络穿透服务、不得泄漏家长PIN/本机Cookie/个人学习数据库；
- GitHub公开，**仅放匿名教学内容，不放个人隐私材料**。

### 分支与目录约定

建议Codex一次性创建独立数据分支 \`detective-inbox\`（可以从当前最终稳定代码分支建立，未来合并main后不影响收件箱历史），初始化目录：
- \`content/detective/inbox/README.md\`：仅约定，不作为运行时内容；
- \`content/detective/inbox/DT-<stable-id>.json\`：**每个错题训练包一个独立JSON**，避免多次会话争用一个总清单；
- \`docs/design/数学小侦探_ChatGPT投递契约_v1.json\`：JSON Schema或Zod/JS校验的可读实例（由Codex维护）；
- \`tests/fixtures/detective-inbox-v1.json\`：匿名样例，**测试夹具不得被当作用户实际投递**。

首版最多200个完整案件；新包3案计3个容量，空间不足明确提示并保留GitHub原件，不能静默丢弃。以后按实际使用扩大容量；不要把“以后10年素材库”挤进单行JSON无限增长。

### 内容同步机制

- 首选：网站启动时同步，之后**每15分钟检查一次**；进入数学小侦探页面时如超过2分钟未同步，可触发异步刷新。家长可选点“立即同步”，但正常使用**无需手点**。
- 只读访问固定 \`lovestream/math-learning\` 和固定 \`detective-inbox\` 分支；不要从聊天文本/URL拼任意仓库、任意域名。
- 推荐只查询 \`content/detective/inbox\` 目录获取文件名+blob SHA，**仅拉取新增/变化的文件**；使用ETag条件请求、合理退避，注意匿名GitHub API速率限制。目录内仅允许符合命名、大小上限的JSON。
- 本地保存\`importedSourceSha\`/源文件路径/整包hash、上次同步时间、错误摘要与导入状态；不能一失败就忘记已导入记录。
- GitHub短暂不可达、403/429/超时：原本训练仍可用；指数退避并在家长端显示“待同步”；绝不能清空本地案卷。
- 先导入私有草稿，再校验、决定发布：同一个包校验失败应**事务性失败**，不把半套训练错乱发布。允许“部分可用/待核对”只能有明确逐案状态与追溯记录。
- 当天计划已生成的，**不能静默替换孩子正在调查的版本**；另设“新到案件”列表支持当日立刻做（需扩展当前\`detectiveAttempt(start)\`只能从今日3案中启动的限制），且保持徽章单案一次、每日最多3枚的边界。
- 自动同步只代表本机读取了文件；同步成功回执仅在**网站本地管理页/同步日志**可见，除非后续实现受保护的回执上传。ChatGPT当前不能仅凭GitHub文件存在“远程知道本机已同步”。

### GitHub访问与安全

- 仓库仍公开，所以读取收件箱不需要将任何个人token写入项目或前端。若未来改成私库，GitHub只读凭证应由家长安全地配置在本机环境（不进仓库、不传给ChatGPT，不借学生网页持有）。
- 内容只来自指定数据分支和目录，实行**代码/数据严格分离**。不得因“信任GitHub”而\`eval\`、执行脚本、接受动态import/HTML、把外部Markdown直接当安全HTML。
- 准入不能单纯依赖 payload 自称\`approved:true\`、ChatGPT自己的\`confidence\`或带的哈希；**本机必须独立校验**。GitHub审计保留提交SHA，可查来源。
- 如需自动信任“由ChatGPT工具提交”，Codex须说明认证/可信分支策略，不能把JSON中\`producer:"ChatGPT"\`当认证；可用指定分支的写入权限＋本机数学校验作为首期信任边界，保留暂停自动发布的家长设置。
- 不新增公网写入接口；如果加入本机\`POST /api/parent/detective/sync\`供手动刷新，必须延续家长PIN+同源/CSRF校验；**后台定时任务不经过伪造家长三项勾选**，应以可信导入类型写入审核来源，而不是假冒用户已审。

## 3. ChatGPT ↔ Codex 共同遵守的JSON投递契约

**原则**：复用已经存在的\`CaseContent\`校验（\`shared/detective-model.mjs\`），不要再次发明一套评分/探案系统。ChatGPT的输出多一层\`bundle\`包装，进入网站后拆为现有\`cases\`、\`versions\`、\`attempts\`。

### v1包装字段（示例；由Codex最终落成可测试schema）

**注意**：这是接口设计实例，不是已经生成/投递的实际错题；\`example\`值不得直接导入儿童题库。实际完整包默认包含3个独立案件，且每一案件都要用真实可执行的验证规则。上面的\`verification.checkedBy\`是期望生成的记录类型，**不能因为ChatGPT自己填了这个字符串就宣称已由服务端验证**。

### 数据契约硬规则

1. 完全复用现有\`CaseContent\`精确字段：\`title,prompt,steps,verdict,errorStep,reasons,reason,repair,verify,hints,solution,family,sourceNotes,visual\`；\`repair/verify\`均按\`kind,question,unit,options,answer\`。\`sourceNotes\`在GitHub**必须空字符串或完全非私人内容**，不得隐藏私聊原题/原图地址。
2. \`case.id\`必须符合现有\`validId\`；\`bundleId\`与文件名从匿名数学条件+题包版本计算稳定去重标识，禁止把姓名、学校、聊天链接放进路径。相同错题多次发送：优先去重；明确“再出不同题”才生成新\`bundleRevision\`。
3. \`visual.kind\`受现有enum和参数约束。当前\`cards\`只能\`["3","2","2厘米"]\`，\`road\`只能\`["10","100"]\`，\`array\`限制小数目。因此**变式B不能擅自继续沿用固定图而换数字**；应选\`visual:{kind:"manual",values:[...]}\`或由Codex真正扩展数学图模型并加数学不变量测试。
4. 家长发来的手写图片里的原始错误可能只有最后答案；必须明确\`simulatedSteps:true\`元数据，模拟学生步骤不得伪称Kevin实际写过的过程。原始图像不进公开repo。
5. 生成的正确案（role=\`correct-control\`）应该与错误案结构相近、条件不相同，且真的完全正确。**第一处错误位置**必须是该案唯一可证实的首错（后面可以有连锁错误），不能造多处独立错误。
6. 数值和排序/表达式必须经**本机第二套数学oracle**验真；不能把ChatGPT给的\`answer\`再次复制为expected就算验证。**当前\`validateCase()\`主要是字段和可解析性校验，不等于数学语义正确性**，需要新增\`verifyImportedCaseMath()\`。
7. 开放解释/图形估计等不宜唯一数值判定的案件，可以ChatGPT先在聊天里问家长澄清；确实无法服务端独立证实时导入为\`needs-review\`。**绝不因为“家长想省事”就把不确定数学内容自动发布给Kevin**。
8. 正确/错误案例都在公共repo匿名展示；即便GitHub raw可被孩子绕过，网站儿童API也必须保留当前分阶段答案隐藏。此方案重在避免在**儿童页面直接泄题**，不声称公开repo中的标准答案对有GitHub访问能力的人绝对保密。
9. 对所有导入保留：\`sourceBranch,sourcePath,sourceBlobSha,bundleId,caseHash,importedAt,mathOracleVersion,importDisposition(auto-published|needs-review|rejected),reason\`。**不要用\`approved:true\`假冒父母批准**；应增加\`approvalSource:"deterministic-import"\`/ \`"parent"\`等明确来源，旧家长审批历史不变。
10. 对源文件大小、字段长度、XSS、HTML、URL、附件引用、数量上限、重复ID、冲突、错误JSON逐项防御；任何校验失败不得改变现有已发布案件和孩子学习记录。

## 4. 数学内容生成规则：一张真实错题如何变成多次训练

### 4.1 优先训练“错误结构”，不复制原题重复刷

例如家长发：\`3张卡共2毫米；Kevin选10张，正确30张\`。

- 原案：识别“组数≠张数”，定位\`10组→10张\`错误；
- 变式案：4张同厚卡总厚3毫米，目标15毫米，某同学误将5组当5张；真实需5×4=20张。**图要随4/3/15变化，不可复用固定3/2/2厘米图**；
- 正确案：5张卡总厚2毫米，目标10毫米，某同学写25张，验证\`25÷5×2=10\`成立。

各题需分别验证数字、单位、第一错误步骤和另一路逆向检查，不将同一份答案硬套。

### 4.2 适合Codex先做可验证模板的范围

第一批确定性模板建议：四则运算及其两步组合、括号顺序、厘米/毫米/分米/米/千米换算、同单位比较及排序、数位换算、等组数量、精确分数等值。每个\`template\`提供独立\`deriveExpected(parameters)\`和\`explainFirstError(steps,parameters)\`，单元测试含正例、误导性错例、边界。

现实长度估计、空间观察、文字有多种解释的题，以及没有完整原题的照片，暂走AI生成私有待核对并在聊天中向用户澄清；不硬套模板、不开“误判发分”。

### 4.3 含多题照片的行为

- 一张照片有多题：ChatGPT先分题编号，保留对应关系；不完整的局部题可单独暂缓，其他完整题照常投递；
- 一道题有多重错因：首版选一个核心“第一处错误”，其他标备注待训练；多错误步骤不能造“只有一个错”的误导题；
- 产生3～5道训练题**不是生成目标本身**：宁可一宗可靠的、有图有证据的案件，也不凑三宗数学不可靠的题；
- 保留家长在聊天中反馈的“这个不是Kevin的错因”“更换难度/图”“再来一组”作为**后续内容修订**依据，重新提交新版本，不默默覆盖旧提交。

## 6. ChatGPT实际执行承诺与反馈文本

后续用户每次说“把这张错题加入数学小侦探”：

- 应先认真识图、核对题意与错误；对完整题生成训练包、核验数值，并通过可用的GitHub连接器**实际调用写入工具**；
- **只有工具成功写入具体分支/路径，才能回复“已写入GitHub”并给提交与路径**；
- 如果GitHub写入被拒、未连接、分支尚未创建或权限不支持，必须如实说明，不能声称已上线；能做的可以先提供可复用训练JSON/Markdown，在Codex恢复时一次性补投递；
- 如果用户上传的照片看不清关键条件、答案多解、数学关系不成立，不把“AI猜测”写成公开的已发布案，可在聊天里问一处关键歧义；
- 网站同步状态与GitHub提交状态分开：**ChatGPT没有远程接收网站回执的工具时只能说“已投递、等待本机自动同步”**。用户可在网站查看新到训练/同步结果；
- 不把整个GitHub PR #1的代码改动当作每次导入案件的常规路径；数据归数据，应用更新归应用更新；
- 家长无需打开Codex复制JSON、无需登录家长后台逐题填写、无需每次点击三项审核。

### 失败与恢复

| 情况 | 用户应看到 | 系统行为 |
|---|---|---|
| ChatGPT成功写入GitHub，但网站此刻没启动 | 已投递，网站启动后同步 | GitHub数据持久，启动时导入 |
| 本地断网或GitHub限流 | 暂未更新，可继续旧训练 | 保留全部本地进度、重试 |
| 同一错题重复发送 | 已有训练，不重复创建 | bundleId+内容指纹去重 |
| 正确答案尚不明确 | 等待补全条件 | 只存私有待审核/不公开儿童案 |
| 数学oracle认为AI内容有误 | 拒绝该案件，指出不一致位置 | 不发布任何错误内容，不修改旧案 |
| Codex改了本地版本但尚未部署 | 等待部署 | 旧网站保持手工能力，新同步不假装有效 |
| GitHub连接器写入遭拦截 | 明确说写入失败、不要声称已同步 | 可以让用户把本次任务交Codex部署，之后重试 |
